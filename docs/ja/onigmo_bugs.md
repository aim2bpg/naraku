# Onigmoのバグ・直感的でない挙動

このドキュメントではNarakuでの修正を予定している、Onigmoのバグと思われる挙動や直感的でない挙動・性質について説明します。

各挙動については後で参照するために固有のID (CF1など) が付いています。
また、バグと思われる挙動には **(BUG)** と、直感的でない挙動には **(UNINTUITIVE)** という印が付けられています。

## バグ、直感的でない挙動・性質

### CF1 (BUG): case folding (`i` フラグ) + 後読み (`(?<=...)`)

OnigmoではUnicodeのfull case foldingを行います。
そのため、 `/ß/i` は `"ss"` にマッチするのですが、後読みと組み合わせた際に問題になります。

例えば、次の正規表現マッチングに失敗します。

```ruby
/(?<=ß)/i =~ "ß" # => nil
```

この挙動は極端に不可解なため、バグであると考えられます。

**Narakuでの対応**:
このバグはOnigmoの後読みの実装がマッチする文字列が固定長のパターンに限定されているために起こるものです。
Narakuでは無制限の後読みをサポートする予定 (**LB1**) なので、自然に解決します。

**実装状況**: ✅ 実装済み — LB1（無制限後読み）が `try_start = 0..closure_pos` の総当たり方式で実装済み。

### CF2 (BUG): case folding (`i` フラグ) + 後方参照

case foldingと後方参照が組み合わさったときに、一貫性のない挙動をすることがあります。
具体的には次のような例で問題になります。

```ruby
/(ß)\1/i =~ "ssß"
```

`/ßß/i =~ "ssß"` や `/(a)\1/i =~ "Aa" `はマッチするので、これはマッチするべきです。
しかし、Onigmoの `i` フラグと後方参照が組み合わさったときの実装にバグがあり、キャプチャされた文字や入力文字列が複数文字にcase foldingされるときに、上手くマッチしなくなっています。

**Narakuでの対応**:
バックリファレンスのマッチングの際にcase foldingを正しく扱うように修正します。

**実装状況**: ✅ 実装済み — `back_ref_match()` が ASCII / Simple / Full fold（ß→ss 等 1-to-N）に対応。

### CF3 (BUG): case folding (`i` フラグ) + 文字クラス

Onigmoの文字クラスのcase foldingにはいくつかの問題があります (CF3からCF5まで)。

複数文字にcase foldingされる文字を含む文字クラスは、文字によってはcase foldingの展開 (unfold) が複数回行なわれることがあります。
例えば `/[abcß]/i` は内部的には `/[abcABCßẞ]|(?i:ss)|(?i:ss)/` に展開されています。
なぜかというと `ß` とその大文字の `ẞ` がunfoldの際に互いに展開されるためです。

これと繰り返しを組み合わせるとReDoSの原因になります。
例えば、次の正規表現は入力文字列 `"x" + "ss" * 30` に対して非常に長い時間 (60秒程度) がかかります。

```ruby
/(x)[abcß]+\1/i =~ "x" + "ss" * 30
```

メモ化を無効にするために後方参照を利用しています。

これは意図した挙動ではないと思われるので、修正したいです。

**Narakuでの対応**:
case foldingの展開の際に、同じ文字に対して複数回展開が行なわれないようにします。

**実装状況**: ✅ 実装済み — Pike VM は構造的に ReDoS 耐性があり重複展開は発生しない。`compile_char_class` が `nk_enc_iterate_case_fold` でクラス内コードポイントの multi-char fold を収集し（ß・ẞ→[s,s] を重複除去）、SPLIT + `compile_full_fold_seq` の alternative として展開。`[ß]/i` が `ss`/`SS`/`Ss` にマッチすることをテストで確認済み。

### CF4 (UNINTUITIVE): case folding (`i` フラグ) + 文字クラスの共通部分 (`[...&&...]`)

Onigmoでは文字クラスの演算をすべて行ったあとにcase foldingを行ないます。
さらに、文字クラスの否定 (`[^...]`) は特別扱いされていて、集合演算として定義されているわけではありません。
それらを組み合わせた場合の挙動は混沌としていて、直感的な理解は困難です。

このため、次の正規表現マッチングに成功するという、不可解な状況が起こります。

```ruby
/[[a-zA-Z]&&[^A]]/i =~ "A" # => 0
```

直感的には `[a-zA-Z]` から `&&[^A]` で `A` を取り除いているのだから、`"A"` にはマッチしないで欲しいように思います。
しかしcase foldingは最後にだけ行われるため、実際には次のように扱われることになります。

1. `[[a-zA-Z]&&[^A]]` を計算し `[a-zB-Z]` が求まる
2. `[a-zB-Z]` をcase foldingした結果、単に `[a-z]` になる
3. 入力文字列 `"A"` をcase foldingすると `"a"` になり、これは `[a-z]` に含まれるためマッチする

この挙動は注意深く考えれば理解できますが、あまり直感的とは言えません。

**Narakuでの対応**:
この挙動に依存しているプログラムも存在するかもしれないので、デフォルトではこの挙動を維持するようにします。
しかし、この挙動を修正できるフラグとして `v` (unicode-set) フラグを提供します。
`v` フラグが有効になった際は、文字クラスの集合演算の各段階で適切にcase foldingを行うようになります。

**実装状況**: ⚠️ デフォルト挙動は維持済み（方針通り）。`v` フラグは未実装。

### CF5 (UNINTUITIVE): case folding (`i` フラグ) + 文字クラスの否定

Unicodeのfull case foldingでは、`ß` が `ss` にcase foldingされます。
そのため `/[ß]/i` は `"ss"` にマッチするのですが、これに文字クラスの否定が組み合わせた際の挙動が一貫していません。

具体的には、文字クラスの否定の際に複数文字にcase foldingされる対応関係は無視されることになります。
そのため、次のマッチング結果になります。

```ruby
/[^ß]/i =~ "ss" # => 0
```

`/[ß]/i =~ "ss"` が位置 `0` でマッチするのだから `/[^ß]/i =~ "ss"` は位置 `0` でマッチして欲しくないように考えられ、あまり直感的な挙動ではありません。

**Narakuでの対応**:
この挙動に依存しているプログラムが無いとは言い切れないので、デフォルトではこの挙動を維持するようにします。
しかし、この挙動を修正できるフラグとして `v` (unicode-set) フラグを提供します。
`v` フラグが有効になった際、否定する文字クラスの中に文字列が存在した場合はエラーになります。

**実装状況**: ⚠️ デフォルト挙動は維持済み（方針通り）。`v` フラグは未実装。

また、case foldingの挙動を制御するための `A`, `S`, `F` フラグを提供することも考えています。
これらは`i` フラグが有効なとき、それぞれ次のような挙動をします。

- `A` フラグ: ASCII case folding。この場合、case foldingはASCII文字の間でしか行なわれなくなります。
  具体的には `A-Z` が `a-z` にcase foldingされるだけになります。
  非常に効率的になるので価値があると考えています。
- `S` フラグ: simple case folding。この場合、case foldingは1対1文字のcase foldingしか行なわれなくなります。
  `A` フラグほどではありませんが、文字クラスの文字が複数文字になることがなくなるので、効率的なはずです。
  `ẞ` (大文字のエスツェット) が `ss` ではなく `ß` (小文字のエスツェット) にcase foldingされるなど `F` フラグと多少の違いがあります。
- `F` フラグ: full case folding。デフォルトの挙動です。これまでと同様に1対複数文字のcase foldingを行います。

加えて、`S`, `F` フラグと同時に `T` (turkish case folding) フラグを指定することもできます。
この場合、`I` が `ı` (ドットの無い小文字のi) にcase foldingされるなどの変化が起こります。
`A` フラグと同時に指定した場合はエラーになります。

### CF6 (BUG): case folding (`i` フラグ) + 連接

`/ss/i =~ "ß"` はマッチします。
しかし、次のパターンはマッチしません。

1. `/\x73s/i =~ "ß"`
2. `/s\x73/i =~ "ß"`
3. `/\u0073s/i =~ "ß"`
4. `/s\u0073/i =~ "ß"`
5. `/\u{73 73}/i =~ "ß"`

これらはエスケープシーケンスはパターンの文字列を区切るため `ss` として認識されないから、`ß` ともマッチしない、という点で一貫しています。
しかし、次のパターンで一方がマッチし、一方がマッチしないのは説明が付かない挙動です。

```ruby
/[s]s/i =~ "ß" # => 0
/s[s]/i =~ "ß" # => nil
```

これはOnigmoでは1文字しか含まない文字クラスが、先頭の場合だけリテラルと同一視するという意味の分からない挙動をしているために起こっています。
この挙動の不一致について合理的に説明することは不可能なので、バグと言って差し支えないです。

**Narakuでの対応**:
いかなる場合でもパターン中に文字クラスとして書かれたものは文字クラスとして扱うようにします。
そのためこの問題は起こらず `/[s]s/i =~ "ß"` はマッチしなくなります。

また、エスケープシーケンスを利用した場合は反対に、一続きの文字列として認識されて、case foldingが適用されるようにしたいと思います。
これは後述するES1の問題と合わせた対応です。Shift\_JISでエスケープシーケンスを使った `\x95\\` が1つの文字 (`"表"`) として扱われるのにも関わらず、case foldingがエスケープシーケンスで区切られるというのも直感的ではありません。
現実的にこのコーナーケースで互換性の問題が生じることは極めて稀だと考えています。

**実装状況**: ✅ 実装済み — 文字クラスは必ず文字クラスとして扱われ `/[s]s/i =~ "ß"` はマッチしない。テスト `test_ascii_fold_cf6_char_class_not_treated_as_literal` で確認済み。エスケープシーケンス連接の対応は ES1 と合わせて未実装。

### CF7 (BUG): case folding (`i` フラグ) + `\w`

`\w` は `i` フラグの影響を受けそうなエスケープクラスですが、影響を受けないことになっています。
しかし、これと集合演算を組み合わせた場合の動作は複雑になります。

例えば、 `/[a-z&&\w]/i` や `/[\w&&a-z]/i` は `K` (U+212A, KELVIN SIGN) とマッチしません。
なぜこうなるのかというと、

- Onigmoの内部では `i` フラグが有効な場合、`cc` と `asc_cc` という2つの集合に文字クラスの中に含まれる文字を集めていきます
- `\w` を追加する際は `cc` には `[a-zA-Z0-9_]` を追加しますが、`asc_cc` には追加しません
- `a-z` を追加する際は `cc` にも `asc_cc` にも `[a-zA-Z0-9_]` を追加します
- `&&` の計算は `cc`, `asc_cc` のそれぞれで行います
  * 今回の場合 `cc` は `[a-z]` になり、`asc_cc` は空集合となります
- 最後に `i` フラグが有効なので `cc` にcase foldingの展開 (unfold) を適用します
  * このとき展開元と展開先のいずれかがASCIIに含まれず、展開先が1文字の場合、展開元が `asc_cc` と `cc` の両方に含まれなければ展開されません
  * つまり `k` から `K` (U+212A, KELVIN SIGN) や `s` から `ſ` (U+017F, LATIN SMALL LETTER LONG S) への展開は行なわれません
  * よって、 `cc` は `[a-zA-Z]` となり、`K` (U+212A, KELVIN SIGN) とはマッチしません
- この動作から、`asc_cc` はASCII外の範囲へのcase foldingの展開を行う範囲を表す集合だと推測できます

また `\w` は `u` フラグの影響を受ける (`/(?u)\w/` は `K` (U+212A, KELVIN SIGN) にマッチする) のです。
このとき `i` フラグと合わせても、`\w` では `asc_cc` への追加は行わないため `/(?u)[a-z&&\w]/i` も `K` (U+212A, KELVIN SIGN) とマッチしません。
これが本当に意図した挙動なのかはよく分からないです。

さらに **CF5** の連接と1文字のみを含む文字クラスの展開が合わさると、より複雑なことが起こります。
例えば `/[k&&\w]/i` や `/[\w&&k]/i` は `K` (U+212A, KELVIN SIGN) とマッチします。
これは `[k&&\w]` の結果が `[k]` となり、1文字のみを含むため単純な文字リテラルとして扱われるためです。

**Narakuでの対応**:
この挙動に依存しているプログラムが存在する可能性があるので、一旦はこの挙動を忠実に再現することにします。
ただし、`v` フラグを有効にした場合はこのような挙動にならず `\w` は集合に単に `[a-zA-Z0-9_]` を追加するものとして扱うつもりです。

**実装状況**: ❌ 未検証 — Onigmo の `cc`/`asc_cc` 二重集合を使った複雑な `\w` + fold 挙動の再現は未実装。`v` フラグも未実装。

### CP1 (BUG): キャプチャ + 先読み

キャプチャと先読みを組み合わせた際に、空文字列のマッチによる無限ループを防ぐための判定のバグにより無限ループになります。
例えば、次のプログラムは停止しません。

```ruby
/((?=(a)))*/ =~ "a"
```

これはかなり予測不可能で、修正すべきです。

しかし、どのように修正するのか決めるのは簡単なことではありません。
なぜなら、Onigmoはループを抜ける判定は、単に空文字列にマッチしたときだけでなく、キャプチャの状態が変化していないことまで要求するためです。

そのため、後方参照と組み合わせると複雑な挙動をします。
例えば、次のプログラムを考えてみてください。

```ruby
/(?:\2()|())*/ =~ ""
$~ # => #<MatchData "" 1:"" 2:"">
```

この正規表現マッチングは次のように行なわれます。

1. 1周目の `(?:\2()|())*`:
   * 左の `\2()` で `\2` がまだ記録されていないので失敗
   * 右の `()` で2番目のキャプチャが記録されてマッチする
2. 2周目の `(?:\2()|())*`: 左の `\2()` で `\2` が記録されているのでマッチし、1番目のキャプチャも記録される
3. 3周目の `(?:\2()|())*`:
   * 左の `\2()` で `\2` が記録されているのでマッチし、1番目のキャプチャも記録されるが、値が前の周と変わっていないので失敗
   * 右の `()` で2番目のキャプチャが記録されるが、値が前の周と変わっていないので失敗
4. `(?:\2()|())*` を抜けてマッチ終了

これだけならまだいいのですが、先読みと組み合わせた場合の挙動は深刻で、現在の判断基準ではキャプチャの状態が振動し、本質的に無限ループとなってしまうパターンが存在します。

```ruby
/((?=(\3a|a))(?=(\2a|a)))*/ =~ "aaaa"
```

この正規表現マッチングは次のように行なわれます。

1. 1周目: キャプチャの状態は `1: "", 2: "a", 3: "aa"`
2. 2周目: キャプチャの状態は `1: "", 2: "aaa", 3: "aaaa"`
3. 3周目: キャプチャの状態は `1: "", 2: "a", 3: "aa"`
   (`\3` が `"aaaa"` なのでこれ以上 `"a"` を追加できず `\3a` でのマッチに失敗し `a` にマッチする)
4. (以下無限ループ...)

この問題に対する解決策は次の2つだと考えています。

1. これまでに生じたキャプチャの状態を全て記録し、過去にあったキャプチャの状態と同じだった場合にループを抜けるようにする
2. 先読みの中のキャプチャの状態はループを抜ける際の判断基準に含めないようにする

**Narakuでの対応**:
2の対応策で行くつもりです。
1の対応策は効率的に実装することが難しいですし、別にそうしたところで2に比べて直感的になるわけでもありません。

2の対応策の詳細な仕様は次のようになります。

- 繰り返し (`*`, `+`など) の中のパターンが空ループを起こす可能性がある場合、ループの開始時点で現在位置と中のパターンに出現するキャプチャの状態を記録します
- 中のパターンに出現するキャプチャには、次のものは**含まれません**
  * 先読み・後読みの中に出現するもの
  * 部分式の呼び出しの、呼び出し先の部分式の中に出現するもの
- 中のパターンにマッチしたときに、開始時点での現在位置とキャプチャの状態を取り出して、現在位置などが変化しているかをチェックします
  * 変化していなかった場合は、その繰り返しは失敗になります

**実装状況**: ✅ 実装済み — ε ビット方式（`MARK_EPSILON` / `CHECK_EPSILON`）で「現在位置が変化したか」のみを判定し、zero-width マッチのループを自動脱出する。方針（捕捉状態の除外判定）より単純だが等価。`/((?=(a)))*/ =~ "a"` は正しく停止する。

### BR1 (UNINTUITIVE): 名前付き後方参照

名前付き後方参照は、同じ名前のキャプチャが複数存在する場合、その後方参照まで出現したものから順番に試行されます。

```ruby
/(?<name>a)(?<name>aa)(?<cap>\k<name>)/ =~ "aaaaa" # => 0
$~[:cap] # => "aa" 
```

しかし、この仕様にはいくつか一貫していない点や、不自然な点があります。

1. 名前付き後方参照のあとに同じ名前のキャプチャが出現した場合、それは後方参照の候補にならない。
   そのため、繰り返しと組み合わさると不自然になる。

    ```ruby
    /(?<name>a)((?<cap>\k<name>)|b(?<name>aa))+/ =~ "abaaaa" # => 0
    $~[:cap] # => "a" (`\k<name>` は最初の `(?<name>a)` しか候補にしないため `"aa"` にはならない)
    ```

2. 条件付きグループ `(?(<name>)yes|no)` で同じ名前のキャプチャが複数存在する場合、最初のキャプチャしか条件の対象にならない。

   ```ruby
   /(?<name>a)?(?<name>b)?(?(<name>)yes|no)/ =~ "ayes" # => 0
   /(?<name>a)?(?<name>b)?(?(<name>)yes|no)/ =~ "byes" # => nil
   ```

3. 深さ指定の後方参照 `\k<name+n>` にした場合、同じ名前のキャプチャが複数存在しても、スタックを辿って最初に見つかったもののみが候補になる。

   ```ruby
   /(?<name>ab)(?<name>ba)\k<name+0>/ =~ "abbaab" # => nil
   # (`\k<name+0>` はスタックを辿って最初に見つかる `(?<name>ba)` しか候補にしないためマッチに失敗する)
   ```

また、名前付きの部分式の呼び出し `\g<name>` は同じ名前のキャプチャが複数ある場合エラーになります。
つまり、重複する名前付きキャプチャの名前の扱いは4種類存在して、全て異なる挙動をしています。

**Narakuでの対応**:
どのケースでも複数存在する場合後に定義されたものを優先して後方参照の候補にして、統一した動作をするようにします。

**実装状況**: ✅ 実装済み — コンパイラが `capture_nums` を逆順に並べた SPLIT チェーンを生成し、最後に定義されたグループを優先する。

### CC1 (BUG): POSIX文字クラス

POSIX文字クラス `[:alpha:]` などのパースは次のようになっています。

1. `[:` が見つかり、無限に先読みして `:]` が見つかった場合、POSIX文字クラスの開始位置として認識する。見つからなかった場合は `[` をネストした文字クラスの開始位置として認識する。
2. POSIX文字クラスの開始位置として認識した場合、`[:` のあとに続く文字列がPOSIX文字クラスの名前と一致するかを確認し、一致して `:]` が続く場合POSIX文字クラスとして認識する。
3. POSIX文字クラスの名前と一致しない場合、20文字以内に `:]` が見つかった場合はエラーにして、そうでない場合は `[:` をリテラルとして認識する。

20文字以内という範囲は内部にハードコードされたもので、特に意味があるとは思えません。
さらに、この挙動のせいで、次のような正規表現のパースに `n` の2乗の時間がかかってしまいます。

```ruby
require 'benchmark'

(1..10).each do |n|
  n *= 10000
  puts Benchmark.measure { Regexp.new('[' + '[:' * n + 'x' * 21 + ':]' + ']') }
end
```

**Narakuでの対応**:
あまり合理的な仕様ではないと考えています。
NarakuではPOSIX文字クラスのパースは次のようにします。

1. `[:` が見つかった場合、POSIX文字クラスの開始位置と仮定して、名前部分の認識を始める。
2. 名前部分の認識の際に `[` や `]` が見つかった場合は、POSIX文字クラスの開始位置として認識するのをやめて、`[` をネストした文字クラスの開始位置として認識する。
3. `:]` が見つかった場合はPOSIX文字クラスの名前と一致するかを確認し、一致している場合はPOSIX文字クラスとして認識する。一致しなかった場合はエラーにする。

この方針であれば線形時間でパースできるはずですし、直感に反する挙動もありません。

**実装状況**: ✅ 実装済み — `lex_posix_char_class_name()` が `[` / `]` に出会うと即座に「unclosed」として返す線形パーサーになっている（`parse.c`）。

### UP1 (UNINTUITIVE): Unicodeプロパティ名

Onigmoでは様々なUnicodeプロパティをサポートしていますが、どのようなプロパティ名をサポートしているか一貫性がありません。
例えば、

- `InCB=Linker` など `InCB` をサポートしていますが、`InCB` の長い別名である `Indic_Conjunct_Break` はサポートしていません。
- `Grapheme_Cluster_Break` の場合は反対に、短い別名の `GCB` はサポートしていません。

- Blockプロパティの値は `In...` の形式で指定できます (`\p{InHiragana}`, `\p{In_Basic_Latin}` など)

**Narakuでの対応**:

他にも一部のプロパティの値を追加したいと考えています。

- `Script_Extensions` (`scx`): マッチングの際に実際に利用したいのは、多くの場合 `Script` ではなくこちらだと思います。
  * 例えば `/\p{sc=Hira}/` は `"ー"` にマッチしませんが、`/\p{scx=Hira}/` はマッチするなど、より自然な挙動が得られます。
- `Canonical_Combining_Class`: サポートしておくことで、Unicodeの正規化の処理の実装に役に立つはずです。

結果的に、NarakuでサポートされるUnicodeプロパティは以下のものになります。

- `Block`
- `Age`
- `General_Category`
- `Script`
- `Script_Extensions`
- `PropList.txt` と `DerivedCoreProperties.txt` で定義されるプロパティ
  * `InCB` を含む
- `emoji-data.txt` で定義されるプロパティ
- `Grapheme_Cluster_Break`
- `Canonical_Combining_Class`

**実装状況**: ❌ 未実装 — 現在は Onigmo 互換の基本プロパティ名のみ対応。`プロパティ=値` 形式・別名の完全対応・`Script_Extensions` 等は未実装。

### UP2 (UNINTUITIVE): Unicodeプロパティとエンコーディング

Onigmoでは様々なエンコーディングをサポートしていますが、Unicodeプロパティの構文のサポート状況はエンコーディングによって異なります。

例えばShift\_JISやEUC-JPなどのJIS系のエンコーディングでは `\p{Han}` のようなプロパティが利用できます。
しかし、同じ漢字圏のエンコーディングであるはずのBig-5などでは `\p{Han}` は利用できません。

これらは一貫しておらず、エンコーディングを実装した人の気分で何がサポートされているか決まっているような状況です。
また、どのエンコーディングで何がサポートしているのかも十分にドキュメント化されていません。

他にも `[[:alpha:]]` などのPOSIXで定義された文字クラスは、デフォルトではUnicodeのエンコーディングの場合はUnicodeプロパティに応じたマッチングをします。
ですが、他のエンコーディングの場合は対応されていないように見えます。
例えば、UTF-8では `/[[:alpha:]]/ =~ "ａ"` (全角文字のa) はマッチしますが、Shift\_JISではマッチしません。

**Narakuでの対応**:
非Unicodeのエンコーディングでは、Unicodeからの変換を使い、元のUnicodeでのプロパティを使ったマッチングができるように修正します。
`d`, `a`, `u` フラグの扱いも同様に一般化します。

しかし、全てのプロパティを非Unicodeのエンコーディングで利用できるようにしてもあまり意味が無いものもあると思いますし、容量の問題もあります。
どこまでサポートするかは容量の増加を見て考えます。

**実装状況**: ❌ 未実装。

### LB1 (UNINTUITIVE): 無制限の後読み

Onigmoは後読み (`(?<=...)` と `(?<!...)`) をサポートしていますが、中のパターンが固定長に分解できる場合に限ります。
例えば `(?<=foo|bar|buzz)` のような後読みはサポートされていますが、`(?<=fo+)` のような後読みはエラーになります。

このサポートしている範囲は実装に依存していて、どこまでサポートしているのか分かりにくいです。
例えば `/(?<a>ab|cd)(?<=a\g<a>a|bb)/` はサポートされていますが、`/(?<a>ab|c)(?<=a\g<a>a|bb)/` はエラーになります。

また、JavaScriptの正規表現など、現代的な正規表現実装は無制限の後読みをサポートしていることが多いです。
そこでNarakuでも無制限の後読みをサポートしようと思います。

**Narakuでの対応**:
後読み用に文字を後ろ向きに読むVM命令を追加し、無制限の後読みをサポートします。
これまでエラーとなっていた部分なので後方互換性の問題は無いはずです。

ただし、書記素クラスタ `\X` の後読み中での扱いは簡単ではありません。
`\X` の後読みを正確に実装するのであれば、Region Indicatorの区切りを見つけるためにさらに後読みをしなければなりません。
現状 `\X` は [UAX #29](https://www.unicode.org/reports/tr29/) の "extended grapheme cluster" の正規表現に展開されていますが、これと後読みが組み合わさった場合の挙動は直感に反することが多いです。
その場合、例えば `/(?<=\X)/ =~ "か\u{309A}"` は3バイト目でマッチすることになりますが、これは直感的ではありません。
そのため、正確な書記素クラスタの実装が提供されるまでは後読み中の `\X` はエラーとすべきです (関連: **GC1**)。

**実装状況**: ✅ 実装済み — 方針では「後ろ向き VM 命令を追加」としていたが、実装は `try_start = 0..closure_pos` の総当たり方式（O(n²)）で等価な結果を達成。`\X` はコンパイルエラーで後読みも不可（方針通り）。

### GC1 (UNINTUITIVE): 書記素クラスタ

Onigmoは書記素クラスタにマッチするパターン `\X` をサポートしていますが、これは単に [UAX #29](https://www.unicode.org/reports/tr29/) の "extended grapheme cluster" の正規表現に展開しているだけです。
そのため、マッチの開始位置が書記素クラスタの境界ではない場合の挙動が直感的ではありません。

この問題に対処するためには `\X` 専用のVM命令を実装して、それを利用するようにし、さらに書記素クラスタの境界以外から始まった場合はマッチに失敗する必要があります。
ただし、これには後方互換性の問題があります。

**Narakuでの対応**:
後方互換性の問題も考えて、一旦は現状の挙動を維持することにします。
つまり、後読み中の `\X` もエラーとします。

もし `\X` の挙動を修正するとしたら、専用のフラグを導入してそれが有効な場合のみ修正された挙動にする (後読み中でも利用可能にする) ことになると思います。

**実装状況**: ⚠️ 方針通り保留 — `\X` はコンパイルエラー（`NK_ERR_UNSUPPORTED_FEATURE`）。

### ES1 (UNINTUITIVE): エスケープシーケンスの前処理

これはOnigmoというよりはRubyの問題です。
Rubyでは自身とエスケープシーケンスの挙動を合わせるために、Onigmoとは別にエスケープシーケンスの前処理を行っています。

ほとんどのエスケープシーケンスはそのままOnigmoに渡されるのですが `\xHH` や `\uHHHH`、`\u{HH...}` などのエスケープシーケンスはRuby側で事前に処理されます。
そのため、いくつかの挙動が予測しづらくなっています。

- Onigmoのドキュメントとの不一致:
  * Onigmoのドキュメントには `\x{HH...}` というエスケープシーケンスが載っているのですが、このRuby側での前処理でエラーにされてしまうため、Rubyから利用することができません
  * そのためRubyからUnicode以外の文字コードの正規表現を書く際に、特定のコードポイントを直接エスケープシーケンスで書くことができなくなっています
  * また、別のエンコーディングの多バイト文字を `inspect` する際にこのエスケープシーケンスが出現することがあります
    + 例えば `puts "藤".encode('Shift_JIS').inspect` は `"\x{93A1}"` と表示されます
    + `puts Regexp.new("藤".encode('Shift_JIS')).inspect` でも同様に `/\x{93A1}/` となります
  * これは `inspect` と `dump` を区別する意図的な挙動らしいので、`\x{HH...}` はサポートしなくていいかもしれません
    + `puts "藤".encode('Shift_JIS').dump` は `"\x93\xA1"` と表示されます
    + `Regexp` には `dump` はありませんが同様の考えだと思われます
- Rubyの挙動との一貫性:
  * Rubyの文字列リテラルのパースとは別のところでさらに処理しているため、部分的に挙動が一致しないところがあります
  * 例えば、Rubyでは `\u{HH...}` 形式のエスケープシーケンスに複数のコードポイントを書く場合、区切りの空白文字に改行 (`\n`) を使えないのですが、正規表現リテラルでは使えてしまいます
- エスケープシーケンスを含めたバイト列がそのエンコーディングで正しいかが正規表現がパースされるよりも先に処理されるため、エラーメッセージが不親切になることがあります。
  * 例えば `Regexp.new('+\x95'.encode('Shift_JIS'))` などで、エンコーディングのエラーが表示されます
  * また、不正なバイト列がエラーメッセージに含まれてしまうこともあります。
    + 例えば `Regexp.new('\x20'.encode('UTF-16LE'))` で出てくるエラーメッセージはそのままではUTF-8にデコードできずエラーになります

**Narakuでの対応**:
どうしてRubyがこのような処理をしているのかというと、正規表現のエンコーディングをOnigmoに渡す前に確定させる必要があるためです。
ただ、それにかこつけてエスケープシーケンスを解釈してバイト列を置換する、という処理をしているためにおかしなことが起こっています。
また、Onigmoが中途半端に渡されたエンコーディングで正しくないバイト列を受け入れられるような設計になっているため、その穴をRuby側で防ごうとしているのも原因の一つです。

この問題への対処として、Narakuでは次のような修正をします。

1. エスケープシーケンスの扱いをRubyの文字列リテラルのパースに近い形にします
   * しかし、エスケープシーケンス + 通常のリテラルの形は例外とします。
     + 全て `\xHH` や `\M-HH` のようなバイトを表すエスケープシーケンスであれば、その部分をまとめて1つの多バイト文字として扱います
     + これは、正規表現のパターンにはUTF-16のようなASCII互換ではない (実質的にバイト列ではない) エンコーディングも利用できるため、その場合に局所的にバイト単位で文字を読むのは不都合が生じるためです
     + 例えばUTF-16BEで `/\x30\x42/` と書いた場合には `"あ"` (U+3042) にマッチしますが、 `/\x30B/` と書いた場合はエラーになります
   * `\u{HH...}` 中の区切りに改行が利用できる問題は修正します
   * `\x{HH...}` はRubyでも対応していないので、サポートしない方針とします
2. 上の修正によりRuby側でのエスケープシーケンスの前処理の必要が無くなります
   * Ruby側で行うのは、パターンの文字列をチェックしてエンコーディングを確定させることだけになります

**実装状況**: ❌ 未実装 — Ruby 側の前処理改善は現 VM プロトタイプのスコープ外。

### ES2 (BUG): エスケープシーケンスの前処理 + 名前付きキャプチャ

Ruby側での前処理は正規表現の構文を完全に考慮しきれていないため、名前付きキャプチャの名前の部分でもエスケープシーケンスを処理しようとします。
しかし、Onigmoは名前付きキャプチャの中のエスケープシーケンスは処理せず、そのまま文字列として扱います。
また、Ruby側の前処理は `0x00..0x7F` の範囲のエスケープされた文字は、再度 `\xHH` としてパターンの文字列に戻す (それ以外はエンコードされたバイト列になる) ことになっているため、これらが組み合わさると一貫性のない挙動になります。
次の例を見てください。

```ruby
/(?<\x61>x)\k<a>/ # raises SyntaxError: undefined name <a> reference

/(?<\u3042>x)\k<あ>/ =~ "xx"       # => 0
/(?<\xe3\x81\x82>x)\k<あ>/ =~ "xx" # => 0
```

1つ目 (`/(?<\x61>x)\k<a>/`) は `\x61` はRubyの前処理後も `\x61` のままのため、 `\k<a>` が解決できずにエラーになります。
しかし、2つ目と3つ目の例では `\u3042` や `\xe3\x81\x82` は前処理で `"あ"` に変換されるため、名前付きキャプチャの名前は `"あ"` になり、 `\k<あ>` も `"あ"` を参照するため、マッチします。

また、Prismは名前の部分のエスケープシーケンスも解釈してしまうため、Prismで `/(?<\x61>x)/ =~ "x"` をパースすると変数 `a` を定義するために `MatchData` の `"a"` を参照しようとして `IndexError` になるという不可解な挙動を引き起こします。

**Narakuでの対応**:
名前付きキャプチャの名前の部分でのエスケープシーケンスもパースするようにします。
つまり、1つ目の例もマッチするようになります。
これは後方互換性を破壊する変更ですが、この挙動に依存するプログラムもあまり存在しないと考えられるため、問題ないと判断しました。

ちなみにECMA-262 (JavaScript) の正規表現でも名前付きキャプチャの名前の部分でのエスケープシーケンスは処理されます。

**実装状況**: ❌ 未実装 — ES1 と合わせた対応が必要で未実装。

### ST1 (UNINTUITIVE): エンコーディング基盤という立ち位置

OnigmoのRubyの正規表現実装だと一般には理解されていますが、実際にはRubyでのOnigmoの立ち位置はエンコーディング基盤かつ正規表現実装と呼ぶ方が正しいです。

しかし、この事実はあまり正しく認識されていません。

この問題のため現在、Prismでは独自のエンコーディングを扱う実装を持つことになっており、Rubyは現在、OnigmoとPrism内部で二重にエンコーディングや文字セットの情報を管理することになっています。

**Narakuでの対応**:
Narakuは「Rubyのための**エンコーディング基盤**および正規表現実装」である、という立ち位置を明確にし、それを意識したAPI設計を行います。

Onigmoでは単に公開されているだけであったエンコーディング部分の実装に、明確なドキュメントを付けて再利用可能なコンポーネントであることを強調します。

**実装状況**: ✅ 方針通り — Naraku はエンコーディング層を独立 API として設計（`include/naraku_encoding.h`）。

### ST2 (UNINTUITIVE): 不正なバイト列の扱い

Onigmoは不正なバイト列を受け入れることができるような設計になっていますが、Ruby側から不正なバイト列を渡すことができず、またどの程度不正なバイト列に対して上手く動作するのかよく分かりません。
また、実装が不正なバイト列を受け入れられるように複雑になっている、コードの意図が分かりにくくなっている、という問題もあります。

**Narakuでの対応**:
Ruby側から利用されない機能の対応のためにコードが複雑・不可解になっているのは好ましくないので、Narakuでは不正なバイト列は受け入れない (パース時・マッチング時にエラーになる) ようにします。

**実装状況**: ✅ 方針通り — 不正なバイト列はパース時にエラー。

### ST3 (UNINTUITIVE): Rubyから見たデッドコード

ST2と関連しますが、Onigmoのコードの中にはRubyからは決して利用されることのない機能がたくさんあります。
例えばRuby以外の構文の対応や、`#define` マクロでデフォルトではオフになっている機能などです。
これらの機能は十分にメンテナンスされているわけではなく、正しく動作するのかも定かではありません。
また、これらの機能のコードが存在することで、コード全体の可読性も著しく下がっています。

**Narakuでの対応**:
Narakuは「Rubyのための正規表現実装」であるという立場のため、Rubyから利用されない機能は削除します。

**実装状況**: ✅ 方針通り — Naraku のコードベースには Ruby から利用されない機能は含まれていない。
